# Tauri v2 移行に関する追加検討事項

このドキュメントは `migration_plan.md` に対するレビュー結果に基づく、移行作業時の追加検討事項およびリスク・対策の補足をまとめたものです。
現在の移行計画を変更することなく、移行作業中のトラブルシューティングや確認事項のリファレンスとして活用します。

## 1. フロントエンドからのプラグインAPI呼び出し（`withGlobalTauri` 環境）

現状のフロントエンドコードは `window.__TAURI__.dialog.message` のように、グローバル変数を介して直接Tauri APIを呼び出しています。
Tauri v2では `dialog` や `shell` などの機能が独立したプラグインに分離されました。

- **懸念事項**: npmバンドラーを使用せず、`tauri.conf.json` の `app.withGlobalTauri: true` に依存している環境下で、v2のプラグインAPIがこれまで通り `window.__TAURI__.dialog` としてグローバルに露出されるかどうか確認が必要です。
- **対策**: フェーズ6または7の動作検証時にAPIが未定義（undefined）エラーとなる場合、プラグイン専用のJSファイル（Tauri提供）をHTML側で明示的に読み込むか、設定でグローバルへのインジェクト方法を調整する必要があります。

## 2. Rust側の `fs` プラグインの要否確認

Tauri v1では組み込みで提供されていたファイルシステムやパス解決のAPIは、v2で `tauri-plugin-fs` に分離されています。

- **懸念事項**: フロントエンドから `fs` APIを直接呼び出していなくても、Rust側（`invoke` コマンドの実装内など）でTauri独自のAPIを利用してパス解決やファイル操作を行っている場合、Rustの依存関係として `tauri-plugin-fs` の導入と初期化が必要になる可能性があります。
- **対策**: フェーズ2（`Cargo.toml` の更新）およびフェーズ5（Rust API移行）において、ファイル操作やパス解決に関連するコンパイルエラーが発生した場合、プラグイン `tauri-plugin-fs = "2"` の追加で対応します。

## 3. イベント送信（emit/listen）のフロントエンドでの購読パス

バックエンド側でのイベント送信機能の変更（`tauri::Emitter`の分離）はマスタープランに記載されていますが、フロントエンドの受信側のパスにも注意が必要です。

- **懸念事項**: v1では `window.__TAURI__.event.listen` を使用してRustからのイベントを購読していますが、v2でグローバル変数の階層構造が変わっている可能性（例：`window.__TAURI__.core.event.listen` など）があります。
- **対策**: フェーズ6（フロントエンド API 移行）の際に、Tauri v2公式ドキュメントの「Events」セクションと照らし合わせ、正しいオブジェクトパスに書き換える作業をタスクに含めます。

## 4. `package.json` 導入の可能性（フォールバック）

- **懸念事項**: 上記のプラグインAPI露出問題（1番目）を純粋な静的ファイル構成のままで解決するのが難しい場合、Tauriの公式JSライブラリ（`@tauri-apps/api` や `@tauri-apps/plugin-dialog` など）を解決するために、npmおよびバンドラーの部分的な導入を検討せざるを得ないリスクがあります。
- **対策**: 本移行プロジェクトにおいては、可能な限り現在のピュアな静的ファイル構成（No node_modules）を維持して解決する方針を最優先としますが、万が一のフォールバック手段として認識しておきます。
