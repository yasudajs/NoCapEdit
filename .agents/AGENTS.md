# プロジェクト固有ルール

## 機能の実装作業の手順
- **実装作業の各ステップは、必ずユーザーの指示を受けてから行うこと。**（計画完了後に自己判断でコード変更などの実装ステップへ自動で進んではならない）

開発は以下のステップに沿って進行する：
1. **ディスカッション**: 機能追加の際には、ファイル修正を行う前に必ずユーザーと修正内容についてディスカッションし、合意を形成する。
2. **ブランチ作成**: AIは現在の開発対象バージョン（v0.1系なら `master`、v0.2系なら `v0.2`）から作業用ブランチを作成する。
3. **バージョン番号の先行更新**: ブランチ作成後**すぐに**、バージョン管理ファイル（Cargo.toml 等の4ファイル）のバージョン番号をあらかじめ次の内部バージョン（v0.1系なら `0.1.x`、v0.2系なら `0.2.x`）に更新しておくこと。（※ここで先に更新しておくことで、その後の実装・テスト中に `Cargo.lock` が自然に同期されるため、必ずこのタイミングで行うこと）
4. **計画策定**: `spec.md` を最新版に更新し、実装計画書 `implementation_plan.md` および `task.md` 等を作成する。実装前提の作業の場合は最初から `docs/[機能名]/` 配下にドキュメントを作成してコミット・プッシュを行う（実装可否が未定の検討案のみ `docs/wip/[機能名]/` を使用する）。
5. **実装と検証**: ユーザーが実装計画書を承認し、実装開始の指示を出した後は、AIは計画に基づいて実装を行う。実装中の進捗保存を目的としたコミット・プッシュは自己判断でこまめに実施してよい。
6. **テスト依頼**: 実装完了後、ユーザーによる手動テストが必要な場合、AIは `task.md` にテスト項目を作成したうえで、ユーザーに手動テストを依頼する。
7. **最終コミット・プッシュ**: ユーザーからテスト完了と承認の指示を受けた**後**に、`docs/history.md` に今回の変更履歴を最上部に追記し、実装したソースコードおよび history.md の更新を含めて最終的なコミット＆プッシュを実行する。
8. **クリーンアップ・マージ**: ユーザーからのクリーンアップ・マージ指示を待つ。

- **実装作業完了後のクリーンアップ・マージルール**:
  ユーザーからクリーンアップまたはマージの指示を受けたら、以下の通り作業ブランチの派生元に応じた処理を追加の確認指示を挟まずに一気に実施する（このフェーズは不要になったドキュメントやブランチの「削除・整理」のみを行う）：

  ### A. v0.1系（作業ブランチが `master` 派生の場合）
  1. `docs/history.md` に今回のバージョンの変更履歴が既に追記済みであることを最終確認する（未追記なら追記する）。
  2. 作業関連のドキュメントフォルダ（`docs/[機能名]/`）を完全に削除してコミット＆プッシュする。
  3. `master` ブランチに切り替え、作業ブランチを非Fast-forwardマージ（`--no-ff`）してプッシュする。
  4. マージ完了後、ローカルおよびリモートの作業ブランチを削除する。

  ### B. v0.2系（作業ブランチが `v0.2` 派生の場合）
  1. `docs/history.md` に今回のバージョンの変更履歴が既に追記済みであることを最終確認する（未追記なら追記する）。
  2. 作業関連のドキュメントフォルダ（`docs/[機能名]/`）を完全に削除してコミット＆プッシュする。
  3. `v0.2` ブランチに切り替え、作業ブランチを非Fast-forwardマージ（`--no-ff`）してプッシュする。**（※絶対に `master` にはマージしないこと）**
  4. マージ完了後、ローカルおよびリモートの作業ブランチを削除する。

- **`master`（v0.1）から `v0.2` への定期同期**:
  - ユーザーから `master` の変更を取り込む指示があった場合、または `master` にバグ修正等がマージされた際は、`v0.2` ブランチに切り替えて `git merge master` を実行し、`v0.2` を最新状態に保つこと。
- 本番リリース（0.1.35など）であれば、ユーザーが配布用のアーカイブファイルのビルドとGitHub CLIでのログイン（gh auth login）を完了したことを受けて、AIはGitHub Releaseへの登録およびREADME.mdの更新を行う。

## Gitの運用方針
- **コミットおよびプッシュのルール**:
  - **実装作業中のコミットおよびプッシュは、AIの自己判断でこまめに実施して良い**（進捗の確実な保存や、問題発生時のロールバックを容易にするため）。ただし、ビルドが通らない状態や不要な一時ファイルをコミットしないよう注意し、コミットメッセージは適切に記述すること。
  - コミットメッセージは日本語で記述する。
  - 1行目を20文字程度で作業内容の概要を記述し、その下に箇条書きで詳細を記述する。
- **マージのルール**:
  - 作業ブランチをマージする際は、ブランチでの開発履歴（分岐と合流）を視覚的に残すため、常に `git merge --no-ff <ブランチ名>` を使用して非Fast-forwardマージを行うこと。

## ドキュメントの運用方針
開発ドキュメント（実装計画書、タスク、ウォークスルー等）のライフサイクルは以下の通りとします。

- **作業ドキュメントの実ファイル化とコミット（コミット漏れ防止）**:
  - AIが生成する実装計画書 (`implementation_plan.md`)、タスクリスト (`task.md`)、ウォークスルー (`walkthrough.md`) は、一時的なアーティファクトで済まさず、必ず `docs/` 配下の適切なフォルダに**実ファイルとして保存し、コミット対象**としてください。
  - 新規作成または更新されたWIPドキュメント（マスタープランや実装計画書など）は、作成・更新された直後、またはそれを用いた具体的な作業を開始する**前**のタイミングで、必ず一度コミットおよびプッシュを行ってください。これにより、Gitの履歴から当時の計画内容を確実に参照できるようにします。
  - **手動テスト時のルール**: 実装した機能に対して手動テスト（動作検証）を行う必要がある場合は、具体的なテスト項目や操作手順のチェックリストを `task.md` に詳細に記述し、ユーザーが検証しやすくすること。

1. **検討中・未確定の構想 (WIP)**:
   - 実装を行うかが未確定なアイディア検討や、将来構想のマスタープラン等は `docs/wip/[機能名]/` 配下に配置します。
   - **【重要】 `docs/wip` フォルダおよびその配下は、将来構想の実装計画やマスタープランが保管されているため、いかなる場合もクリーンアップや削除の対象にしてはならない。**
2. **実装計画の作成 (実作業ワークスペース)**:
   - 実装することが合意・前提となっている作業は、最初から `docs/[機能名]/` 配下に実装計画書（`implementation_plan.md`）やタスクリスト（`task.md`）を作成します。（`docs/wip/` を経由する移動手順は不要）
   - ※もし `docs/wip/` にあった構想を本番実装に移す場合は、対象フォルダを `docs/wip/` から `docs/[機能名]/` へ**移動**します。
3. **実装完了時 (クリーンアップ)**:
   - 開発が終了し、ソースコードとドキュメントがGitにコミット＆プッシュされた後は、クリーンアップフェーズにて対象のドキュメントフォルダ（`docs/[機能名]/`）を完全に削除します。（詳細はクリーンアップ・マージルールを参照）
   - 過去の履歴はGitのコミット履歴で管理するため、リポジトリ内に古いフォルダやファイルを残さないでください。

- **最新版のみの維持**:
  - 常に現在進行中の作業、または全体の共通設計に関する最新のドキュメントのみを残すようにしてください。
  - 機能追加するときには、実装計画書の作成前に `spec.md` を最新版に更新し、その後、実装計画を作成すること。
  - docs/wip/refactor_v0.2_separation_master_plan.md に関する作業を実施している間は、`spec.md`の更新は不要とする。

- **他ブランチや他バージョンからの変更取り込み時の履歴（history.md）記載ルール**:
  - 別ブランチ（メンテナンス版など）で既に実施・記録済みの変更を取り込む際は、`docs/history.md` に「Ver X.Y.Z の変更（またはバグ修正・改善）を取り込み」のように同期である旨を明記し、具体的な内容はファイル内に重複して並列記載せず、その下にインデントして記載すること。

## リリース運用方針
- **内部バージョン**:
  - v0.1系: 変更ごとに `0.1.x` を1ずつインクリメント（小変更は統合可）
  - v0.2系: 変更ごとに `0.2.x` を1ずつインクリメント（小変更は統合可）
- **本番リリース**: 原則5ステップごと（v0.1系であれば 0.1.30, 0.1.35, 0.1.40...）にGitHub Releaseを作成
- **緊急修正**: 必要に応じて例外的に即リリース可
- **GitHub Release**: 本番リリース時のみ作成（内部バージョンではReleaseを作成しない）

## バージョン番号の管理ファイル
バージョンアップ時は、以下の**4ファイルを必ずセットで更新**すること。更新漏れはビルド成果物のバージョン不一致の原因になる。

| ファイル | 該当箇所 | 備考 |
|---|---|---|
| `Cargo.toml` | `version = "x.y.z"` | Rustビルドのバージョン管理 |
| `tauri.conf.json` | `"version": "x.y.z"` | Tauriバンドルのバージョン（アプリタイトルバー等に使用） |
| `nsis/installer.nsi` | `VERSION` / `VERSIONWITHBUILD` | NSISインストーラーのバージョン（`x.y.z.0` 形式） |
| `docs/DEVELOPMENT.md` | ZIPファイル名中のバージョン文字列 | ポータブル版ビルドコマンド例 |

以下は参照・記録用のため、バージョンアップ時の自動更新対象外（内容に応じて手動追記）:
- `docs/history.md` — 変更履歴の追記
- `README.md` — 本番リリース時のダウンロードリンク更新

## コーディング規約

### 1. 定数・設定値の一元管理 (バックエンド)
- バックエンド（Rust）側で新しい定数、設定値、ファイル名ホワイトリスト、数値の上限値などを追加・変更する際は、コード内に直接ハードコード（マジックナンバー化）せず、必ず `src/constants.rs` に定数として定義し、そこから参照する設計にすること。

### 2. 将来の多言語化対応 (フロントエンド)
- **UI表示テキストの `src/dist/i18n.js` 転記徹底**:
  - 機能追加や既存改修において、画面表示に関わる作業（ダイアログ文言、ステータス表示、ボタンラベル、ツールチップ、エラーメッセージ等）を行う際は、コード内に日本語テキストを直接ハードコードせず、必ず `src/dist/i18n.js` へ定義を追加・転記して `t('キー名')` 経由で呼び出す設計にすること。
  - 新規テキストの追加時だけでなく、修正・改修対象のコード周辺に関係するハードコードテキストがある場合も、あわせて随時 `i18n.js` へ切り出してリファクタリングを進めること。
  - 実装計画書（`implementation_plan.md`）作成時にも、画面表示に関する変更が含まれる場合は `i18n.js` への転記・追記対象を事前に確認・明記すること。

### 3. 既存共通モジュール・定数の事前確認と共通化方針 (フロントエンド/バックエンド)
- **実装前の共通処理・定数の検索徹底**:
  - 新機能の実装や改修を行う際は、ファイル修正を行う前に必ず既存の共通モジュールを確認し、処理や定数の重複作成・直書きを防止すること。
  - **バックエンド (Rust)**: 定数・設定値・ファイル名ホワイトリスト・数値の上限値などは、必ず `src/constants.rs` を確認し、既存の定数があれば参照、なければ同ファイルに追加して使用する。
  - **フロントエンド (JS)**: パス結合（`joinPath`）・ファイル名抽出（`getFileNameFromPath`）・親パス取得（`getParentPath`）・パス比較正規化（`normalizePathForComparison`）・日時生成等の汎用処理は、必ず `src/dist/js/utils/helpers.js` や `src/dist/js/state.js` を確認し、既存の共通関数を使用するか `helpers.js` に追加して使用する。
- **実装計画書への明記**:
  - 計画策定時（`implementation_plan.md` 作成時）に、事前調査として既存の共通定数・ヘルパー関数の活用方針および新規追加対象があるかを必ず検討・明記すること。
